## 一、项目背景

### 1.1 为什么做这个项目

现有 Markdown 软件试了一圈，没有一个能顺手长期用，主要问题集中在四类：

| 问题 | 具体表现 |
|---|---|
| 功能臃肿 | 笔记库、知识图谱、模板中心、插件市场一堆用不上的东西，真正每天要用的功能反而埋得深 |
| 强制云端 | 必须登录账号、必须同步、文件存在别人的服务器上，本地文件反而成了二等公民 |
| 使用感粗糙 | 长文档滚动掉帧、输入有延迟、暗色模式做得敷衍 |
| 改不动 | 开源或闭源的都改不了自己要的那一点，只能忍着 |

结论：与其继续忍，不如自己做一个。**功能不求多，但每一处都必须是自己在用时顺手的那一种。**

### 1.2 项目目标

1. 做一个**本地优先**的 Markdown 编辑器：文件始终在自己硬盘上，不依赖任何账号和网络。
2. 做一个**轻量**的产品：启动快、占用低、安装包小。
3. 做一个**Windows / macOS / Linux 三端体验一致**的编辑器：换电脑不用换习惯。
4. 用 AI 辅助编程（vibe coding）完成开发，控制迭代成本，**避免功能越加越乱**。

### 1.3 成功标准（怎么算做成了）

- 能完全替代自己现在用的 Markdown 软件，日常写作不需要再切回旧工具；
- 打开 1MB 的 md 文件、滚动、输入全程无卡顿感；
- 安装包体积控制在 20MB 以内，内存常驻不超过 200MB；
- 自己每周愿意继续用它写东西，不装完就吃灰。

## 二、目标用户与使用场景

### 2.1 目标用户

只有一个：项目作者本人（技术从业者，日常写文档、笔记、草稿）。不做多用户、不做团队。

### 2.2 核心使用场景

| 场景 | 描述 | 频率 |
|---|---|---|
| 写技术文档 | 打开某个仓库里的 `docs/xx.md`，在一个页面里边写边看到最终排版（表格、代码块） | 每天 |
| 随手记 | 新建一个 md 或 txt 文件，快速写几行想法，随手保存 | 每天 |
| 整理长文档 | 打开一篇几千字的稿子，改结构、调格式、加章节 | 每周 |
| 导出分享 | 把 md 导出成 HTML / PDF 发给别人 | 偶尔 |

## 三、产品定位与边界

### 3.1 定位

> **一个文件夹 + 一堆 `.md` 文件 + 一个干净的编辑窗口。**

不做笔记管理平台，不做知识库，只做「打开文件 → 写字 → 保存」这件事，并把它做到顺手。

写作体验对标 Typora：**一个画布，写什么立刻长成什么样**，不需要在「源码模式」和「预览模式」之间来回切。

### 3.2 明确不做（非目标）

以下功能一律不做，避免项目失控：

- ❌ 云同步、多端同步
- ❌ 账号体系、登录注册
- ❌ 团队协作、评论、分享链接
- ❌ 双链笔记、知识图谱、标签体系
- ❌ 插件市场、主题商店、模板中心
- ❌ 移动端 App（Tauri 虽支持，但本期不做）
- ❌ 自建 Markdown 渲染内核（直接复用成熟组件）
- ❌ 左右分屏预览、源码模式 ↔ 预览模式的切换（只有一种编辑形态）
- ❌ 图片相关能力：粘贴插入、拖入、自动保存到本地、本地图片预览（本期一律不做，后续再评估）

## 四、功能需求

优先级说明：**P0 = 第一版必须有（没有就不能用）；P1 = 第二版必须有（没有就不好用）；P2 = 后续可选。**

### 4.1 P0 — 核心闭环（v0.1）

| 编号 | 功能 | 需求描述 |
|---|---|---|
| F-01 | 打开本地文件 | 通过系统文件对话框打开单个文件，**仅支持 `.md` / `.markdown` / `.txt`**；`.txt` 按纯文本编辑、不渲染 Markdown；支持命令行参数或拖拽文件到窗口打开 |
| F-02 | 保存文件 | `Ctrl/Cmd + S` 保存到原路径；未保存时窗口标题有未保存标记 |
| F-03 | 另存为 | 支持保存到新路径，并切换当前编辑目标 |
| F-04 | 编辑区 | 一个干净的编辑区，支持 Markdown 常用语法输入，无多余工具栏干扰 |
| F-05 | 单页即时渲染（Typora 式） | **只有一个画布**：在同一页面内边写边渲染，光标所在段落显示可编辑的 Markdown 源码，其余段落直接呈现最终排版样式；**不做左右分屏、不做编辑/预览模式切换** |
| F-06 | 语法渲染 | 标题、粗斜体、列表、任务列表、引用、链接、行内代码、代码块（带语言高亮）、表格、分割线、脚注；图片语法不渲染、不加载 |
| F-07 | 文件夹打开 + 文件树 | 打开一个文件夹，左侧显示文件树，**仅列出 `.md` / `.markdown` / `.txt`**；点击切换当前编辑文件；隐藏文件与其它类型文件不显示 |
| F-08 | 新建文件 | 在当前文件夹新建 `.md` 文件，可命名；新建后自动进入编辑状态 |
| F-09 | 未保存保护 | 关闭窗口 / 切换文件前若有未保存内容，弹窗提示「保存 / 不保存 / 取消」 |
| F-10 | 编码兼容 | 默认 UTF-8；打开非 UTF-8 文件时给出提示，不出现乱码静默写入 |

### 4.2 P1 — 日常顺手（v0.2）

| 编号 | 功能 | 需求描述 |
|---|---|---|
| F-11 | 暗色模式 | 提供浅色 / 深色 / 跟随系统三种模式，正文与代码块配色一致 |
| F-12 | 大纲面板 | 侧栏显示当前文档的标题大纲，点击可跳转到对应位置（`.txt` 不显示大纲） |
| F-13 | 查找替换 | 当前文档内搜索，支持高亮全部匹配、上下跳转、替换单个 / 全部 |
| F-14 | 快捷键 | 新建、打开、保存、另存为、查找、切换侧栏、切换暗色模式 |
| F-15 | 最近打开（仅本机） | 记录最近打开的文件夹与文件，启动时可快速继续；**只存本机，各端互不同步，不做跨端迁移** |
| F-16 | 字数统计 | 状态栏显示字数 / 字符数，实时更新 |
| F-17 | 导出 HTML | 导出带样式的独立 HTML 文件；文中已有的图片链接按原样保留，不做下载、不做内嵌 |
| F-18 | 自动保存草稿 | 每秒防抖写入临时草稿，崩溃或异常退出后可恢复 |

## 五、非功能需求

### 5.1 性能指标

| 指标 | 要求 |
|---|---|
| 冷启动时间 | 3 秒内出主窗口（常规配置 SSD） |
| 打开文件 | 1MB 的 md 文件 500ms 内可编辑 |
| 输入延迟 | 打字无可感知延迟，长文档末尾输入不掉字 |
| 即时渲染 | 输入后段落转渲染态无可感知延迟，不闪屏、不跳动 |
| 内存占用 | 单文档常态 ≤ 200MB |
| 安装包体积 | ≤ 20MB（不含用户文档） |
| 大文件保护 | 超过 5MB 的文件打开时提示，避免卡死 |

### 5.2 平台要求

| 平台 | 最低版本 | 交付形式 |
|---|---|---|
| Windows | Windows 10 64 位 | `.exe` 安装包 / 免安装 |
| macOS | macOS 11+（Intel / Apple Silicon） | `.dmg` |
| Linux | 主流发行版（AppImage 优先） | `.AppImage` |

三端功能保持一致，允许渲染细节有平台差异，但**核心交互不得缺失**。

### 5.3 数据与安全

- 所有文件读写仅限用户主动选择的文件与文件夹，不扫描全盘；
- 不做任何网络请求（无遥测、无统计上报、无云调用）；
- 不修改用户文件内容以外的任何系统设置；
- 删除、覆盖只发生在用户明确触发的操作中。

### 5.4 体验要求

- 界面克制：不放常驻工具栏、不放弹窗广告、不做引导教程；
- **编辑形态唯一**：任何时候都只有一个编辑画布，不出现分屏按钮、不出现「源码 / 预览」开关；
- 所有默认值可接受：装完直接能用，不需要先配置；
- 中文界面优先，术语用中文。

## 六、验收标准（第一版 v0.1）

逐条可测，全部通过才算「能用」：

1. 双击打开一个 `.md` 文件，内容完整显示，标题、列表、表格、代码块渲染正确；
2. 在同一个画布内输入 Markdown 语法，离开该段落光标后内容立刻变为最终排版，界面中**不存在分屏或模式切换入口**；
3. 打开一个 `.txt` 文件，按纯文本显示，Markdown 符号不被渲染；
4. 修改内容后 `Ctrl+S`，用其他编辑器打开确认内容已写入，且无多余空行、格式未被破坏；
5. 打开一个含 50 个文件的文件夹，左侧文件树正确列出（只含 md / txt），点击切换不报错、不丢内容；
6. 编辑后不保存直接关窗口，弹出保存提示，三个选项行为都正确；
7. 打开 1MB md 文件，滚动与输入无卡顿；
8. 关闭网络后所有功能正常（验证无远端依赖）；
9. 三端分别安装后，上述流程一致可复现。

## 八、给 AI 编码的约束（防跑偏）

写代码时按此约束执行，避免反复返工、成本失控：

1. 只实现当前需求条目的功能，**不主动新增清单外的功能**；
2. 不引入清单外的新依赖，需要用新依赖先说明理由；
3. 改动后必须列出「改了哪些文件、每个文件改了什么」；
4. 不擅自重构已完成且验收通过的模块；
5. 每次改动给出可执行的验证步骤，验证通过再提交；
6. 遇到不确定的产品细节，先提问，不凭猜测定稿。
